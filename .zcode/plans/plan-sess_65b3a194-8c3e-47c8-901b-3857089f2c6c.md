# llm-style — Mood-based Outfit Recommender (Architecture Plan)

## The core architectural insight

With 100–300 wardrobe items and a small local LLM (3–8B), we **cannot** dump the whole wardrobe into the prompt — small models degrade badly past a few hundred tokens and get slow. The architecture is therefore built on a two-stage engine:

1. **Deterministic candidate selection** (SQL filtering in Python): weather → warmth band, occasion → formality band, guaranteed coverage of each clothing slot. Narrows 300 items to ~20 candidates.
2. **LLM as the stylist's final judgment**: given only the compact candidate list + mood + context, it picks the winning combination and explains *why it matches the mood* — the one thing rules can't do (mood maps to color/texture/vibe, a fuzzy judgment small models handle well when the search space is small).

**Rejected alternatives:**
- *Full wardrobe in prompt* — fails at 100–300 items with small models (bloat, degradation, latency).
- *Embedding/vector retrieval* — more machinery (vector store, embedding model) for no gain: mood-to-clothing similarity is fuzzy, and SQL filtering already does the narrowing better for this scale. YAGNI.

## Components & responsibilities

**1. API layer** (`FastAPI`, `backend/app/main.py`)
- `POST /api/outfits/recommend` — `{mood, occasion, weather_override?}` → `{outfit: [items], rationale}`
- `GET/POST/PUT/DELETE /api/items` — wardrobe CRUD
- `GET /api/weather` — current weather for configured city
- `GET/PUT /api/settings` — city, model name, Ollama URL
- Serves the static frontend itself — one process, `uvicorn app.main:app` and done.

**2. Wardrobe data model** (SQLite via stdlib `sqlite3`; Pydantic schemas for API)
`items`: `id, name, type (top/bottom/shoes/outerwear/accessory), color, warmth (1–5), formality (1–5), style_tags (e.g. "streetwear, minimal"), notes, times_worn`
`settings`: single row — `city, model, ollama_url`. `outfit_history`: `created_at, mood, occasion, weather_json, item_ids_json, rationale` (cheap now, enables feedback later).

**3. WeatherService** — Open-Meteo (free, no API key): temp, rain, wind for the configured city; 30-min cache; on failure fall back to last cached value and let the user override manually in the UI.

**4. CandidateSelector (deterministic core, fully unit-tested)**
- Temp → warmth band: ≥24°C→1, 17–23→1–2, 10–16→2–3, 4–9→3–4, <4→4–5; outerwear slot only offered below ~14°C.
- Occasion → formality floor: gym 1 / casual 1 / work 2 / smart 3 / formal 4; keep items within [floor, floor+2].
- **Mood is deliberately NOT filtered here** — that's the LLM's job.
- Cap candidates: ≤8 per required slot (top/bottom/shoes), ≤4 for optional slots (outerwear/accessory), random-sampled seeded by the date (variety day-to-day, reproducible within a day).
- If a slot is empty → relax warmth band one step and retry → if still empty, return a named gap ("no items warm enough for 2°C") so the UI can tell the user what to add.

**5. LlmStylist (LLM integration)**
- Thin `LlmProvider` interface with an Ollama implementation (`/api/chat` with structured JSON output). Local-only per your choice, but the interface means a hosted model can be added later without touching the engine.
- Default model configurable in settings (e.g. `qwen3:4b` or `llama3.2:3b` — solid small models for structured JSON), temperature ~0.7 for styling creativity.
- Prompt: personal-stylist system role + compact candidate list (id, type, color, tags, warmth, formality) + mood + occasion + weather summary. Output: `{item_ids: {top, bottom, shoes, outerwear?, accessories[]}, title, rationale}`.
- **Validation loop**: every returned ID must exist in the candidate set and required slots must be filled; one retry with the validation error appended; if it fails again → deterministic fallback assembly (highest formality-fit pick per slot) so the user never gets an error page — just a plainer rationale.

**6. RecommendationService** — orchestrates: fetch/override weather → select candidates → call stylist → validate → log to history → return. Single entry point, easy to test with a fake LLM + in-memory DB.

**7. Frontend** — vanilla JS + fetch, no build step, served by FastAPI. Three views:
- **Ask** (home): mood textarea, occasion select, weather chip (auto-filled, clickable to override), → result card: outfit items with names/colors + stylist's rationale.
- **Wardrobe**: filterable grid/table + add/edit form (type, color, warmth, formality, tags).
- **Settings**: city, model name.
- Structured for one outfit now; the response shape is already a list of options-compatible objects so adding "2–3 ranked outfits" later is a UI change, not an API redesign.

## Error handling summary
- Weather API down → last cache → manual override in UI.
- Ollama down / invalid JSON → retry once → deterministic fallback outfit (with note that it's the fallback).
- Empty candidate slots → explicit gap message naming what's missing.
- All API errors as JSON `{detail}` with proper 4xx/5xx codes.

## Testing
- **pytest unit tests** for CandidateSelector (the deterministic core — warmth bands, formality floors, slot coverage, gap detection, caps) and prompt building (golden files).
- **Service tests** with a fake LlmProvider (scripted responses: valid, invalid JSON, wrong IDs) and temp SQLite DB.
- One opt-in smoke test hitting real Ollama (`@pytest.mark.integration`).

## Build sequence
1. Scaffold + config + SQLite schema + items repo + CRUD API (working immediately via curl).
2. Frontend wardrobe page (CRUD UI) — the app is useful as a wardrobe catalog already.
3. Settings + WeatherService (Open-Meteo, cache, fallback).
4. CandidateSelector + full unit tests — the deterministic heart.
5. LlmProvider (Ollama) + LlmStylist prompt/validation/fallback, tested with fakes.
6. RecommendationService orchestration + history logging + `POST /api/outfits/recommend`.
7. Frontend Ask page (mood → outfit card with rationale).
8. Seed script + README + end-to-end smoke test.

Each phase ends with something demonstrable. Prerequisites on your machine: Python 3.11+, Ollama installed with a small model pulled (e.g. `ollama pull qwen3:4b`).
